# Migrating To 0.19.0: Provider-Neutral Credentials

Version `0.19.0` moves secret-provider ownership outside danvas. Danvas now
consumes one explicitly selected environment variable or one single-purpose
credential file. It no longer imports, invokes, or diagnoses a password manager,
loads local dotenv files, or accepts provider-specific options and profile keys.

Read this guide before replacing a `0.18.0` installation. Authentication is the
only major product boundary changed in this release; Canvas mutation, private
artifact, source-layout, and evidence contracts remain unchanged.

## Who Will See The First-Run Failure

Many existing initialized projects will fail on their first Canvas-backed
command after the upgrade. The common `0.18.0` setup has a project
`[canvas].api_url`, no matching selected user profile, and a default
`CANVAS_API_KEY`. A project URL can no longer decide where that token is sent.

The failure occurs before danvas reads the token. Fix it in exactly one of these
ways:

1. Define a matching user profile and add `profile = "example-university"` to
   the project's existing `[canvas]` table.
2. Export `CANVAS_API_URL` with the exact same HTTPS origin as the project URL.
3. Pass the same origin with `--api-url` for that invocation.

The profile is the recommended durable fix:

```toml
# Platform user configuration: danvas/config.toml
[profiles.example-university]
api_url = "https://canvas.example.edu/"
api_key_env = "CANVAS_API_KEY"
```

```toml
# Course project: .danvas/config.toml
[canvas]
course_id = 101
api_url = "https://canvas.example.edu/"
profile = "example-university"
```

Do not add credential selectors to the course project. Course repositories are
not trusted to choose which token danvas reads.

## Workflow Migration Matrix

### Environment-backed SecretPath profile

Before (`0.18.0`):

```toml
[profiles.example-university]
api_url = "https://canvas.example.edu/"
secret_provider = "env"
api_key_env = "CANVAS_EXAMPLE_API_KEY"
```

After (`0.19.0`):

```toml
[profiles.example-university]
api_url = "https://canvas.example.edu/"
api_key_env = "CANVAS_EXAMPLE_API_KEY"
```

The external process must provide `CANVAS_EXAMPLE_API_KEY`. Danvas reads that
one variable, removes it from its environment before Canvas construction, and
does not fall back when it is missing or invalid.

### Direct 1Password reference

Before (`0.18.0`):

```toml
[profiles.example-university]
api_url = "https://canvas.example.edu/"
secret_provider = "1password"
op_reference = "op://Example/Canvas/credential"
```

After (`0.19.0`), keep only the neutral danvas profile:

```toml
[profiles.example-university]
api_url = "https://canvas.example.edu/"
api_key_env = "CANVAS_API_KEY"
```

Let 1Password own resolution and process injection:

```bash
export CANVAS_API_KEY='op://Example/Canvas/credential'
op run -- danvas auth doctor \
  --profile example-university --check-canvas
```

The exported value is a 1Password reference, not the Canvas token. `op run`
resolves it and launches danvas with the resulting environment. This example is
optional and follows the official
[1Password `op run` reference](https://www.1password.dev/cli/reference/commands/run).
Danvas does not inspect the reference or contact 1Password.

### Optional SecretSpec runner

An individual or organization may define `CANVAS_API_KEY` in its own
SecretSpec manifest and a scope that exposes only that value:

```toml
[project]
name = "danvas-credentials"
revision = "1.0"

[profiles.default]
CANVAS_API_KEY = { required = true }

[scopes.danvas]
secrets = ["CANVAS_API_KEY"]
```

Run danvas beneath the external resolver:

```bash
secretspec run --scope danvas -- \
  danvas auth doctor --profile example-university --check-canvas
```

The syntax and scoped child-environment behavior are documented by the official
[SecretSpec CLI reference](https://secretspec.dev/reference/cli/#run) and
[scope guide](https://secretspec.dev/concepts/scopes/). Danvas does not ship a
SecretSpec manifest, SDK, provider choice, or configuration.

### Platform or container credential file

Point the profile at an absolute, externally managed file:

```toml
[profiles.example-university]
api_url = "https://canvas.example.edu/"
api_key_file = "/run/secrets/canvas_api_key"
```

Or select the path for one process:

```bash
CANVAS_API_KEY_FILE=/run/secrets/canvas_api_key \
  danvas auth doctor --profile example-university --check-canvas
```

The file contains exactly one token with an optional terminal LF or CRLF. Danvas
requires an absolute path, a regular file, at most 16 KiB, and no NUL or other
line break. It supports projected-volume symlinks through a single opened file
descriptor, but rejects files contained inside the active course project.
Danvas never creates, edits, chmods, rotates, or deletes the source file.

### Multiple Canvas instances

Use a matching profile and a different neutral locator for each origin:

```toml
default_profile = "example-university"

[profiles.example-university]
api_url = "https://canvas.example.edu/"
api_key_env = "CANVAS_EXAMPLE_API_KEY"

[profiles.other-university]
api_url = "https://canvas.other.example/"
api_key_file = "/run/secrets/canvas_other_api_key"
```

A selected profile whose URL disagrees with the effective Canvas URL now fails
before credential access. Danvas never assumes tokens are interchangeable.

## Selector Precedence

Credential input selection is independent of URL selection:

1. `--api-key-env` or `--api-key-file`;
2. the selected profile's `api_key_env` or `api_key_file`;
3. `CANVAS_API_KEY_ENV` or `CANVAS_API_KEY_FILE`; and
4. the default environment value `CANVAS_API_KEY`.

Selecting both transports at one layer is an error. Once one locator wins,
failure is final; danvas does not try another variable, file, or provider.

The two CLI values and the two process-selector values are locators, never raw
tokens. `CANVAS_API_KEY` is the token value only when no higher-precedence
locator was selected.

## Dotenv Loading Was Removed

Danvas no longer discovers or parses `.env`. A file in the working directory
cannot change the Canvas URL or token used by the command.

Do not replace the old behavior with a committed plaintext dotenv file. If an
external tool consumes a reference-only environment file, that tool owns its
format, permissions, and resolution. For example, 1Password documents
`op run --env-file=PATH -- <command>` for files containing 1Password references;
danvas sees only the resulting process environment.

## Auth Doctor Schema Changed

`danvas auth doctor` now reports only the boundary danvas owns:

- profile and effective Canvas origin;
- origin-binding state;
- selected environment or file transport;
- missing, unreadable, invalid, or resolved input state;
- path-free POSIX permission warnings; and
- the optional bounded Canvas current-user check.

JSON output uses `danvas-auth-doctor-v1` with `origin`, `credential`, `canvas`,
and `issues` objects. The `0.18.0` SecretPath-shaped JSON is not an additive
schema predecessor and must not be parsed as the new format. Provider tool
availability, configuration files, provider references, and provider errors
are intentionally absent.

Run offline first:

```bash
danvas auth doctor --profile example-university
```

Add `--check-canvas` only to authorize the bounded current-user request:

```bash
danvas auth doctor --profile example-university --check-canvas
```

Ordinary authenticated commands now say only
`Using Canvas credential from: environment` or
`Using Canvas credential from: credential file`. Danvas cannot truthfully
attribute a value to an external provider it did not contact.

## Roster Schema Removal

Roster export now has one schema with these headings:

```text
CanvasID,Name,LoginID,SIS_ID
```

The `0.18.0` `roster --schema legacy-v1` option is removed and fails as an
unknown option. Remove it from automation and update readers that still expect
the old `Email` label. Danvas's internal compatibility reader still accepts
either historical header where an existing input artifact requires it, but new
roster exports are `LoginID`-only.

## Delivery Risk Is An Operator Choice

The supported transports move data; they are not secret stores:

- A global shell export can persist for the session and reach unrelated child
  processes.
- A per-command external runner narrows exposure to its launched process tree,
  subject to that runner's own guarantees and provider credentials.
- A durable plaintext `.env` file is a secret-bearing artifact that danvas no
  longer discovers.
- A single-purpose credential file can fit container and platform mounts, but
  its protection still depends on filesystem, mount, user, and host policy.

Danvas removes a selected environment variable before its own downstream work.
It does not claim memory zeroization or protection from same-user process
inspection, administrators, debuggers, or crash dumps.

## Install, Verify, And Roll Back

Before upgrading, preserve your user configuration and identify every stale
profile. Danvas does not rewrite it automatically.

After the tag exists, replace the exact tool version:

```bash
uv tool uninstall danvas-cli
uv tool install \
  "danvas-cli @ git+https://github.com/olearydj/danvas.git@v0.19.0"
uv tool list
danvas --version
danvas auth doctor
```

Verify one configured instance with `--check-canvas` before an operational
command. Do not begin with a Canvas-changing command merely to test credentials.

To roll back without rewriting project files:

```bash
uv tool uninstall danvas-cli
uv tool install \
  "danvas-cli @ git+https://github.com/olearydj/danvas.git@v0.18.0"
uv tool list
danvas --version
```

Rollback restores the old executable only. Keep a backup of the `0.18.0` user
profile if you need its provider-specific keys during rollback. Course project
files need no authentication migration and should not be rewritten for either
direction.
