# Migrating To 0.16.0: Private Artifact Boundary

Version 0.16.0 changes where danvas stores student-identifying and otherwise
private artifacts. It also protects those files from the moment they are
created, removes private row detail from routine terminal output, and reduces
machine-specific provenance in report manifests.

This is a behavior-changing alpha release. Review automated workflows before
upgrading.

## Platform And Filesystem Contract

Private artifact commands are supported on POSIX platforms in this release.
Danvas creates its own private directories with mode `0700` and private files,
including temporary files, with mode `0600`. It does not rely on the process
umask or write first and chmod later.

Private writes do not overwrite by default. Commands that expose `--overwrite`
replace an artifact through a private temporary file. A standalone CSV, text,
or binary artifact has a same-directory integrity sidecar. Private JSON embeds
its classification. A missing sidecar or SHA-256 mismatch means the pair is
invalid and should be regenerated.

When a `.danvas` project is discoverable, omitted private destinations resolve
beneath `.danvas/private/`. Outside a project, pass the command's explicit
`--output`, `--output-dir`, or `--rollback-dir` before Canvas can be contacted.

## Command Changes

- `roster` now defaults to `.danvas/private/roster.csv`. The default columns
  are `CanvasID,Name,LoginID,SIS_ID`. `--schema legacy-v1` temporarily retains
  the old `Email` header; the value remains the Canvas login ID and is not
  verified as an email address.
- `assignments overrides` defaults to
  `.danvas/private/overrides/assignment-<id>.yaml`.
- Explicit `gradebook check`, `gradebook audit`, and `quiz analysis` outputs
  use private creation and no-clobber behavior. Their private report runs use
  the protected report root described below.
- `submissions export` and `submissions grades` default under
  `.danvas/private/submissions/assignment-<id>/`.
- `submissions media` defaults to the assignment's private `media/` bundle.
  Student-derived filenames are allowed inside that protected bundle, but are
  no longer printed individually. Existing `.part` files are refused and are
  never deleted as though danvas created them.
- `submissions feedback --dry-run` defaults to the private
  `feedback-plan.json`; a subsequent live run defaults to the distinct
  `feedback-results.json`, so the normal preview-then-upload sequence does not
  overwrite either artifact. An explicit `--output` remains a single
  no-clobber destination. The command prints only aggregate matched,
  unmatched, uploaded, and failed counts.
- Live `grades post` and `grades clear` write rollback and recovery evidence
  under `.danvas/private/grades/assignment-<id>/rollback/`. Outside a project,
  live use requires `--rollback-dir`. Grade plans, results, and verification
  output no longer print student names, IDs, scores, grades, or comments.
- `grades comments` defaults to a private assignment/user path and prints only
  the bounded assignment artifact root.
- `discussions export` defaults to
  `.danvas/private/discussions/topic-<id>/posts.json`.
- `discussions score` always writes a private `grade-plan.csv` by default and
  prints aggregate counts rather than participant names and scores. Its legacy
  direct `--upload` behavior is otherwise unchanged in 0.16.0.
- `announcements export` defaults beneath `.danvas/private/announcements/`.
  It remains private even when only the authenticated instructor's replies are
  selected because `--reply-user-id` can select another participant.
- `recordings panopto-captions` defaults beneath
  `.danvas/private/recordings/panopto-captions/`. Caption files and manifests
  are private; manifests no longer retain viewer, launch, signed, verifier, or
  session URLs.

Explicit private destinations remain supported. If an explicit destination is
outside a discovered project's `.danvas/private/`, danvas warns that it can
protect the artifact itself but will not change unrelated ancestor directory
permissions.

## Reports And Provenance

Private report runs now live under `.danvas/private/reports/`. Non-private
reports remain under `.danvas/reports/`. `danvas reports list` and
`danvas reports latest` search both roots, so existing report history remains
discoverable. If both roots contain the same run-directory name, discovery
keeps both by reporting their storage scope.

Manifest schema version 2 removes full `argv` and absolute run/project paths.
Input provenance is project-relative or recorded only as external. Existing v1
manifests remain readable and are not rewritten.

Source-map provenance no longer falls back to an absolute path. A source used
by a provenance-writing command must be inside the selected project root. The
stable error is:

<!-- markdownlint-disable MD013 -->

```text
Source is outside the danvas project root; move it into the project or pass the correct --project-root.
```

<!-- markdownlint-enable MD013 -->

Move the source into the project or pass the project root that actually
contains it. Dry-run and live resolution enforce the same boundary.

If an existing `.danvas/source-map.json` contains an absolute `path`, first
move or confirm the source beneath the project root, then replace that value
with its project-relative POSIX path, such as `content/case.md`. If the old
entry cannot be bound confidently, remove only that entry and rerun the
appropriate synchronization workflow to recreate its provenance.

## Git Tracking And Existing Artifacts

New Git-backed projects initialized by danvas add these generated locations to
`.gitignore`:

```gitignore
.danvas/course.json
.danvas/reports/
.danvas/private/
```

`.danvas/config.toml` and `.danvas/source-map.json` are stable, non-secret
course configuration and provenance. They may be tracked in a private course
repository, but they are `course_internal`, not automatically public-safe.
Inspect course names, object IDs, schedules, and deployment history before
publishing them. Tokens never belong in either file.

Adding an ignore rule does not untrack a committed file. Inspect a specific
known artifact before changing the index:

```bash
git ls-files -- .danvas/private/ path/to/known-export.csv
git rm --cached -- path/to/known-export.csv
```

Danvas does not run `git rm`, delete old exports, or rewrite Git history. A
history rewrite does not retract data from an already-public clone. Rotate any
suspected credential, and use the applicable institutional/privacy process for
student data that entered published history.

## Canvas File Downloads

`files download` and `files download-one` remain `course_internal`, because
Canvas file metadata cannot prove that an instructor-uploaded file contains no
student data or restricted material. Choose an explicit private destination
when file contents are sensitive. Danvas does not infer sharing rights or scan
payload contents in this release.
