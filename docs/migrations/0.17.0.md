# Migrating To 0.17.0: Plan Before Canvas Mutation

Version 0.17.0 makes omission safe across the Canvas-writing command surface.
Commands that can change Canvas now plan by default. Add `--apply` to authorize
the reviewed operation; `--dry-run` remains an explicit spelling for the same
plan mode.

This is a behavior-changing alpha release. Existing automation that relied on
a bare command mutating Canvas must be updated before upgrading.

## Common Mutation Contract

For the fifteen commands that can still write Canvas:

- omitting both mode flags plans and performs no Canvas write;
- `--dry-run` also plans and performs no Canvas write;
- `--apply` authorizes the planned Canvas mutation;
- `--dry-run --apply` is an error before project resolution, authentication,
  output creation, or Canvas access; and
- no profile, environment variable, or project setting restores live writes
  on omission.

Planning may read Canvas and may write the command's normal report or private
plan artifact. A ready or no-change plan exits `0`; blockers and unreliable
planning exit nonzero. A successful plan exit therefore does not mean Canvas
was changed.

The most important automation risk is deliberately safe but silent: a legacy
script that runs one of the thirteen formerly bare-mutating commands now plans
and exits `0`. Scripts must add `--apply` when they intend a write and inspect
the retained result status or evidence instead of treating process success
alone as proof of mutation.

## Applying Reviewed Plans

The ordinary workflow is plan, review, then apply:

```bash
danvas assignments update content/assignments/case.md
danvas assignments update content/assignments/case.md --apply
```

`--dry-run` remains useful when an operator or script wants to state plan mode
explicitly:

```bash
danvas grades post --assignment-id 202 --grades-csv grades.csv --dry-run
danvas grades post --assignment-id 202 --grades-csv grades.csv --apply
```

Additional guards remain additive. Assignment upsert requires the confirmation
that matches its plan, and override reconciliation requires its exact
confirmation:

```bash
danvas assignments upsert SOURCE --apply --confirm update
danvas assignments overrides-sync SOURCE --apply --confirm apply
```

Do not combine `--dry-run` with `--apply`. On override sync, do not combine the
deprecated `--live` alias with either new mode flag.

## Discussion Scoring Automation

`discussions score --upload` now exits nonzero deliberately after generating
the grade plan. Automation should distinguish this migration signal from plan
generation failure by checking that the private grade-plan artifact exists and
passes its integrity check, then use the grade transaction:

```bash
danvas discussions score DISCUSSION_URL 2 2 3 2 --output grade-plan.csv
danvas grades post --assignment-id ASSIGNMENT_ID --grades-csv grade-plan.csv
danvas grades post --assignment-id ASSIGNMENT_ID --grades-csv grade-plan.csv --apply
```

The generated CSV includes `CanvasID`, `Grade`, `ExpectedCurrentGrade`,
`Comment`, and `CommentAction: append`, plus review-only activity counts.
`grades post` tolerates those extra columns and preserves the expected-state
guard and transactional readback behavior.

## Feedback Preflight And Results

Feedback planning and applying continue to use distinct no-clobber defaults:

- plan: `.danvas/private/submissions/assignment-<id>/feedback-plan.json`;
- apply: `.danvas/private/submissions/assignment-<id>/feedback-results.json`.

In 0.17.0, any unmatched feedback file is a blocker. Fix the filename/roster
match or narrow `--pattern`, then create a fresh plan. Apply preflights every
target before the first write, recognizes one exact existing comment/attachment
as `already_applied`, checkpoints after each row, reads each attempted row
back, and stops after rejection, pre-acceptance failure, uncertainty, or any
other unsafe result.

If Canvas accepted a request but readback failed, the row is
`accepted_unverified`. Inspect Canvas and retain the evidence; do not rerun the
row blindly because doing so could duplicate a comment or attachment.

## File Upload Conflicts

`files upload` now defaults to `--on-duplicate error`. Under that policy a
known name collision blocks before upload. Immediately before a planned create,
danvas re-lists the destination and uses Canvas's rename transport so a race
cannot overwrite an existing file. If Canvas returns a different name, or a
stable file ID without a verifiable name, danvas records an unsafe outcome and
exits nonzero. The race can leave a new renamed file; inspect it manually and
do not retry blindly.

Overwriting or intentional renaming requires both explicit policy and apply:

```bash
danvas files upload FILE --folder "course files/slides" \
  --on-duplicate overwrite --apply
danvas files upload FILE --folder "course files/slides" \
  --on-duplicate rename --apply
```

Assignment-integrated asset uploads keep their separate `error`/`rename`
policy and existing source-map verification contract.

## Local-Write Dry Runs Are Unchanged

These four commands use `--dry-run` to control retained local file writes, not
Canvas mutation:

- `pages sync`;
- `announcements sync`;
- `discussions sync-prompts`; and
- `recordings panopto-captions`.

They keep their 0.16.0 behavior and do not expose `--apply`. Read-only,
download, export, and inspection commands likewise do not gain `--apply`.

## Privacy And Retained Evidence

The 0.16.0 private-artifact boundary remains in force. Grade, feedback,
discussion-scoring, rollback, and recovery artifacts stay beneath
`.danvas/private/` by default. Routine stdout remains aggregate and sanitized.
Evidence may retain stable Canvas IDs needed for verification and recovery but
does not retain credentials, signed URLs, or raw transport payloads.
